# Группы внутри команды — второй выпуск (витрины)

Дата: 2026-08-31
Ветка: `feature/team-subgroups`
Спека: [2026-08-31-team-subgroups-design.md](../specs/2026-08-31-team-subgroups-design.md)
Первый выпуск: [2026-08-31-team-subgroups.md](2026-08-31-team-subgroups.md)

## Что уже есть после первого выпуска

Реестр команд с признаком деления, группы, приписка сотрудника, группа у задачи
(явная + резолвер лесенкой), колонка в стопке разбора, ёмкость и сценарий в
разрезе групп, секции в ресурсном планировании, второй уровень фильтра в шапке.

Фильтр в шапке уже кладёт выбранные группы в параметры запроса
(`subgroups`) — **бэкенд их пока игнорирует везде, кроме стопки разбора**.
Второй выпуск учит витрины этот параметр понимать.

## Решения, принятые до плана

1. **Материализованная группа задачи.** Резолвер лесенкой ходит вверх по
   родителям в Python — для витрин, которые считают агрегаты в SQL по сотням
   тысяч задач, это неприменимо. Заводится колонка «действующая группа» у
   задачи, которую пересчитывает та же фаза, что пересчитывает категории.
   Витрина получает обычное условие `WHERE`, как по команде.
   Побочно: колонку видно в экспортах и отчётах без второго прохода.
2. **Кто чем режется.** Факт — по группе задачи; всё, что считается «на
   человека» — по группе человека:
   - по задаче: Дашборд (кроме баланса часов), Аналитика, Проекты, Бэклог,
     экспорт отчёта;
   - по человеку: KPI, Стол тимлида, баланс часов, ёмкость.
3. **Executive не дробится** — раздел верхнеуровневый, показывает команду
   целиком. Фильтр группы туда не течёт, как и в ресурсное планирование.
4. **Переток внутри команды** показывается в трёх местах: Ресурсы (расход
   ёмкости группы), Дашборд (третья строка баланса часов рядом с «помощью
   извне»), Аналитика (строка в шапке отчёта).
5. **Команда без групп — ноль изменений.** Все новые условия включаются только
   при непустом списке групп, а он не может быть непустым у команды без
   признака. Пересчёт действующей группы обходит только команды с признаком.

## Фаза 1 — фундамент

### Task 1: Действующая группа у задачи

Колонка `effective_subgroup_id` (FK на группы, `SET NULL`) + индекс.
Alembic, batch mode, идемпотентно как миграция первого выпуска.

`SubgroupResolver.recompute_effective(team: str | None = None) -> int`:
- команды без признака пропускаются, их задачи получают `NULL`
  (чтобы снятие признака чистило хвост);
- задачи команды грузятся одним запросом вместе с `parent_id`;
- лесенка считается в памяти по построенной карте родителей, без N+1;
- пишет только изменившиеся строки, возвращает число изменений.

Тест `tests/services/test_subgroup_effective.py`:
- лесенка явно > родитель > исполнитель совпадает с `resolve_for_issue`;
- снятие признака у команды обнуляет колонку;
- повторный прогон не пишет ничего (возвращает 0).

Verify: `py -3.10 -m pytest tests/services/test_subgroup_effective.py -v`

### Task 2: Когда пересчитывать

Точки вызова:
- `MappingService.recalculate_all()` — после пересчёта категорий (синк);
- `MappingService.recalculate_for_issues()` — точечно по командам этих задач;
- подтверждение группы в стопке (`PUT /issues/{id}/subgroup`) — по команде задачи;
- правка приписки сотрудника (`PUT /employees/.../team`) — по этой команде;
- правка реестра (признак деления, удаление/переименование группы) — по команде.

Тест `tests/test_subgroup_recompute_triggers.py`: снятие приписки у сотрудника
меняет предположение у его задач без ручного пересчёта.

Verify: `py -3.10 -m pytest tests/test_subgroup_recompute_triggers.py -v`

### Task 3: Единая разборка параметра

`app/services/subgroup_filter.py`:
- `parse_subgroups_csv(raw) -> list[str]` — как `parse_teams_csv`;
- `issue_clause(ids)` — `Issue.effective_subgroup_id.in_(ids)` либо `None`;
- `employee_subgroup_ids(db, ids, teams)` — множество сотрудников,
  приписанных к выбранным группам (для «людских» витрин);
- `subgroup_names(db, ids)` — подписи для заголовков и экспортов.

Пустой список — все функции возвращают `None`/пусто, вызывающий код не меняет
запрос. Это и есть гарантия «команда без групп ведёт себя как раньше».

Тест `tests/services/test_subgroup_filter.py`: пустой вход не даёт условий;
идентификатор чужой команды отбрасывается.

Verify: `py -3.10 -m pytest tests/services/test_subgroup_filter.py -v`

## Фаза 2 — задачные витрины

### Task 4: Дашборд

`GET /analytics/dashboard/{norm-work,categories,projects}` и
`/dashboard/hours-balance` принимают `subgroups`.

- «Категории» и «Проекты» — по группе задачи;
- «Нормированные работы» и «Баланс часов» — по группе человека
  (нормированные работы привязаны к людям, спека, п.5);
- «Помощь извне» на группы не реагирует — граница «свои-чужие» остаётся
  на уровне команды.

Тест `tests/test_dashboard_subgroups.py`: сумма по группам равна показателю
команды; выбор одной группы не меняет «помощь извне».

Verify: `py -3.10 -m pytest tests/test_dashboard_subgroups.py -v`

### Task 5: Аналитика

`GET /analytics/report` принимает `subgroups`; условие ложится рядом с
`_apply_team_filter` — по группе задачи, независимо от галочек
«по сотруднику / по задаче» (галочки решают принадлежность команде, группа
уточняет уже отобранное).

Тест `tests/test_analytics_subgroups.py`: сумма часов по группам равна отчёту
по команде; задача без группы попадает в выборку «Без группы».

Verify: `py -3.10 -m pytest tests/test_analytics_subgroups.py -v`

### Task 6: Проекты

`GET /projects` и сводка портфеля принимают `subgroups`: проект остаётся в
выдаче, если у него есть хотя бы одна задача выбранной группы; часы и оценки
считаются только по задачам выбранных групп.

Тест `tests/test_projects_subgroups.py`.

Verify: `py -3.10 -m pytest tests/test_projects_subgroups.py -v`

### Task 7: Бэклог

Элементы бэклога привязаны к задаче Jira — группа берётся у задачи. Ручные
идеи задачи не имеют, поэтому от фильтра групп **не прячутся** (тот же приём,
что уже сделан для фильтра команд).

Тест `tests/test_backlog_subgroups.py`: ручная идея видна при любой группе.

Verify: `py -3.10 -m pytest tests/test_backlog_subgroups.py -v`

приписке, показатели считаются как раньше. Профили по ролям не трогаем.

Тест `tests/test_kpi_subgroups.py`: сумма сотрудников по группам равна составу
команды; сотрудник без приписки попадает в «Без группы».

### Task 9: Стол тимлида

Verify: `py -3.10 -m pytest tests/test_team_desk_subgroups.py -v`

## Фаза 4 — переток внутри команды

### Task 10: Расчёт перетока

`app/services/subgroup_flow_service.py`:
`flow(team, from_, to_) -> {subgroup_id: {out_hours, in_hours}}` —
часы, где группа сотрудника ≠ группа задачи, обе внутри одной команды.
Часы «на сторону» (`out`) — расход ёмкости своей группы, «пришло»
(`in`) — усиление чужой. Помощь извне (чужая команда) сюда не попадает.

Тест `tests/test_subgroup_flow.py`:
- разработчик группы 1 на задаче группы 2 даёт `out` первой и `in` второй;
- работа сотрудника чужой команды в переток не попадает;
- сумма фактов по группам с учётом перетока сходится с фактом команды.

Verify: `py -3.10 -m pytest tests/test_subgroup_flow.py -v`

### Task 11: Показ перетока

Три места, один и тот же расчёт:
- **Ресурсы** — строка под ёмкостью группы: «ушло к соседям / пришло от них»;
- **Дашборд**, виджет баланса часов — третья строка между «своими» и «помощью
   извне»;
- **Аналитика** — строка в шапке отчёта, когда выбрана группа.

Verify: собрать фронт (`npm run build`), проверить на команде без групп —
строк нет, вид прежний.

## Приёмка выпуска

1. Команда без включённого деления ведёт себя идентично текущей версии на всех
   восьми витринах.
2. Сумма по группам равна показателю команды везде, где есть разбивка.
3. Часы разработчика из чужой группы: факт у группы-заказчика, расход ёмкости
   у своей группы, переток виден строкой.
4. Помощь извне на группы не реагирует.
5. Executive и ресурсное планирование фильтру группы не подчиняются.
6. Сотрудник и задача без группы видны в строке «Без группы», а не теряются.
7. Полный прогон: `py -3.10 -m pytest tests/ -v` (кроме `tests/api/test_llm.py` —
   зависает без сети).
