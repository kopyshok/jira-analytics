# Поток 8. «Быстродействие» — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Шаги — чекбоксы.

**Goal:** рабочее место админа «Быстродействие»: замеры каждого запроса к API, минутные агрегаты,
детали медленных запросов, снимок нагрузки сервера раз в минуту, хранение 30 дней, экран с графиком,
узкими местами, медленными запросами и выводом «сервер занят другим / медленный наш код», выгрузки
`.md` для разработки и Excel.

**Спека:** `docs/superpowers/specs/2026-10-04-q4-improvements-pack-design.md`, раздел «Поток 8».

**Architecture:**
- `app/core/perf.py` — сборщик в памяти (агрегат «минута × метод × шаблон пути», гистограмма по
  корзинам для 95-го процентиля, буфер медленных), счётчик обращений к базе через события
  SQLAlchemy `before/after_cursor_execute` на классе `Engine` + `contextvars` (объект статистики
  запроса кладёт промежуточный слой; поток пула видит его через копию контекста).
- `app/core/perf_middleware.py` — чистый ASGI-слой (не `BaseHTTPMiddleware`): шаблон пути из
  `scope["route"].path` после маршрутизации; пропуск не-`/api/`, своих `/api/v1/admin/perf*`,
  потоков `text/event-stream`, несматченных путей; время — до последнего куска тела (фоновые задачи
  ответа не считаются); CPU процесса за время запроса (`time.process_time`) для вывода.
- `app/models/perf.py` + миграция `pf01_perf_metrics` (идемпотентно): `perf_minute`,
  `perf_slow_request`, `perf_server_snapshot`.
- `app/services/perf_writer.py` — сброс агрегатов пачкой, снимок `psutil` + пул + запросы в работе,
  чистка старше `perf_retention_days`; асинхронный цикл в `lifespan`, работа с базой в потоке,
  любая ошибка — лог и пропуск.
- `app/services/perf_report.py` — чтение за период (1h/24h/7d/30d), узкие места (сортировка по
  суммарному времени), медленные с деталями, ряд для графика, вывод по каждому медленному запросу,
  выгрузки `.md` и `.xlsx` (openpyxl).
- `app/api/endpoints/admin_perf.py` — `/admin/perf/overview`, `/report.md`, `/export.xlsx`, admin-only.
- Фронт: `api/perf.ts`, `components/settings/PerformanceTab.tsx`, пункт «Быстродействие» в группе
  «Администрирование» `SettingsPage`.

**Отклонение от спеки (осознанное):** корзины гистограммы — отдельные целочисленные колонки
`h0..h10`, а не JSON: так 30 дней агрегатов суммируются одним `GROUP BY` в базе, без выгрузки
сотен тысяч строк в Python. Переносимо на SQLite и PostgreSQL.

**Settings:** `perf_enabled=True` (в тестах `PERF_ENABLED=false` через conftest), `perf_slow_ms=2000`,
`perf_flush_seconds=60`, `perf_retention_days=30`.

**Вывод по медленному запросу** (порядок проверки):
1. сервер ≥ 85% и наш процесс < 30% (доля машины) → «похоже, ресурсы занял кто-то другой»;
2. время в базе ≥ 50% длительности → «долгая работа с базой»;
3. CPU процесса за время запроса ≥ 70% одного ядра или процесс в ту минуту ≥ 80% ядра →
   «медленный наш код»;
4. иначе → «ожидание: не процессор и не база (например, ответ Jira)».
Нет снимка — шаг 1 пропускается.
