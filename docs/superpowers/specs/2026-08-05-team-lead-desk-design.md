# Рабочий стол тимлида — дизайн

Дата: 2026-08-05
Ветка: `feature/team-lead-desk` (отводится от main)
Макет: https://claude.ai/code/artifact/4b60ca0f-6900-4b58-bcdd-a2e740ec54d4

## Зачем

Руководитель разработки следит за задачами своих разработчиков: где работа встала, кто не укладывается в оценку, что не разбито на подзадачи. Сейчас в сервисе есть рабочий стол аналитика (публичный монитор по ссылке, один сотрудник). Стол тимлида — другой сценарий: внутренний раздел, много людей сразу, акцент на отклонения.

Раздел видят все авторизованные пользователи. Ограничений по ролям на первом этапе нет.

## Что тимлид выбрал

Реализуем **все три раскладки** одного и того же набора данных. Тимлид переключается табами и решает в бою, какая удобнее. Выбранная раскладка запоминается за пользователем.

- **A · Светофор** — карточки-плитки, одна на разработчика. Клик по карточке фильтрует таблицу задач.
- **B · Ведомость** — та же сводка таблицей со шкалами и строкой «Итого». Клик по строке фильтрует таблицу задач.
- **C · Проблемы вперёд** — лента признаков-фильтров, под ней одна таблица задач, сгруппированная по разработчику. Шкала расхождения другая: засечка оценки посередине, влево недобор, вправо перебор.

## Данные

### Новое из Jira

Два поля добавляются в сопоставление полей на странице настроек, рядом с уже настроенными:

| Поле в Jira | Тип | Куда |
|---|---|---|
| «Разработчик» (`customfield_14052`) | пользователь | новое поле задачи: имя + идентификатор учётной записи |
| «DEV est (ч)» (`customfield_12952`) | число | новое поле задачи: оценка разработки, часы |

Поля заполняются и на задачах, и на подзадачах. Значение подзадачи — её собственное, не наследуется от родителя.

После добавления полей нужна перезаливка задач проекта OS (обычная синхронизация, поля подтянутся вместе с остальными).

### Факт часов

Факт берём **из списаний времени** (worklog), не из поля «DEV spent (ч)». Причина: поле в Jira не даёт разбивки по людям, а сводка по разработчикам — суть раздела. Одно число из двух источников не должно расходиться на экране.

Факт по задаче = сумма списаний всех сотрудников. Разбивка по конкретному разработчику доступна при раскрытии строки.

### Кому принадлежит задача

Задача попадает в срез разработчика по полю «Разработчик» самой задачи. Если у подзадачи стоит другой человек — подзадача идёт в срез своего разработчика, а в родительской строке видна с пометкой имени.

### Отсутствия

Существующий справочник отсутствий (отпуск / больничный / командировка / обучение / отгул) с цветами. Новых сущностей не нужно.

### Состав команд

Через существующий механизм периодов участия: состав команды считается на дату, выбывшие в расчёт не попадают.

## Настройки раздела

Всё, что может поменяться, — настройка, а не константа в коде. Живут в общих настройках приложения, редактируются на экране раздела (панель «Пороги») и/или на странице настроек.

**Пороги подсветки:**

| Настройка | Значение по умолчанию |
|---|---|
| Декомпозиция обязательна от | 16 ч |
| Перерасход от | 30 % |
| Недорасход от | 50 % |
| Зависла, дней в статусе | 5 |
| Оценки подзадач ниже родителя на | 25 % |
| Лимит задач в работе одновременно | 3 |

**Группы статусов** — таблица «статус → группа», редактируемая. Статусная модель в Jira меняется, поэтому список не зашивается.

| Группа | Статусы по умолчанию |
|---|---|
| У разработчика | В РАБОТЕ, КОД-РЕВЬЮ, ФИЧА-РЕВЬЮ, Ожидает помещения |
| Ждут не его | Ожидает тестирования, Тестирование, У инициатора, Ожидает обновления |
| Не начаты | Backlog, К выполнению |
| Закрыты | ГОТОВО, Отменено |

Статус, не попавший ни в одну группу, показывается в разделе «прочее» и не ломает расчёты. Новый статус из Jira подсвечивается в настройках как нераспределённый.

**Тип подзадачи** — какие типы задач считаются декомпозицией. По умолчанию «Подзадача» (стандартный подчинённый тип Jira).

## Правила подсветки

Семь признаков. Каждый вычисляется по задаче и по подзадаче отдельно; признаки декомпозиции — только по задачам верхнего уровня.

| Признак | Условие |
|---|---|
| Перерасход | факт больше оценки на «перерасход, %» и выше |
| Недорасход | задача закрыта и факт меньше половины оценки (порог «недорасход, %») |
| Без декомпозиции | оценка больше порога декомпозиции и нет ни одной подзадачи |
| Подзадачи недооценены | сумма оценок подзадач ниже оценки родителя на «оценки подзадач ниже родителя, %» |
| Нет оценки | оценка не заполнена |
| Нет списаний | оценка есть, списанных часов ноль, задача не закрыта |
| Зависла | задача не закрыта и висит в текущем статусе дольше порога |

Недорасход считается только по закрытым задачам — иначе каждая начатая задача горит жёлтым в первый же день.

Перерасход считается и по открытым задачам тоже — это самый ранний сигнал, ради него раздел и делается.

## Состав экрана

**Шапка (общая для всех раскладок):**
- команды — мультивыбор
- отдельные разработчики — добираются точечно поверх команд, когда нужен один человек из чужой команды
- период — «Открытые сейчас» (по умолчанию) или квартал из общего фильтра
- шестерёнка «Пороги» — раскрывает панель настроек

**Сводка по разработчикам** (вид зависит от раскладки): задач всего, из них у него / ждут не его / не начаты, факт и оценка со шкалой, точность оценок (медиана отношения факта к оценке), значки признаков с количеством.

**Детальная таблица задач:** ключ, название, статус с пометкой группы, разработчик, оценка, факт, шкала, дней в статусе, признаки. Строки раскрываются в подзадачи. Сортировка по колонкам. Фильтр по разработчику — кликом по сводке.

**Задач в работе одновременно:** горизонтальные полосы по людям с отсечкой лимита, превышение красным.

**Отсутствия:** лента-календарь, строка на разработчика, цветные отрезки по типам, выходные затемнены.

## Что не делаем

Обсуждали и сознательно отложили:
- **возвраты задачи в разработку** (сколько раз уезжала назад из тестирования) — тимлид не просил, история статусов доступна, вернёмся при необходимости;
- **прогноз «успеет / не успеет»** (остаток оценки против свободных часов с вычетом отпусков) — требует связки с планированием ресурсов, отдельная работа.

## Проверки

- перезаливка проекта OS подтягивает разработчика и оценку разработки в задачи и подзадачи;
- каждый из семи признаков срабатывает на подготовленных данных и не срабатывает на граничных значениях порога;
- смена порога в настройках меняет подсветку без перезапуска;
- статус, не отнесённый ни к одной группе, не ломает сводку;
- разработчик, выбывший из команды в середине периода, не попадает в срез;
- подзадача с другим разработчиком считается за ним, а не за владельцем родителя;
- переключение раскладки сохраняется между входами.
