# Группы внутри команды — дизайн

Дата: 2026-08-31
Ветка: `feature/team-subgroups`

## Задача

Внутри одной команды существуют несколько устойчивых групп, которые сопровождают
и развивают разные направления и планируются на квартал раздельно. В Jira этого
деления нет и не будет — оно живёт только в сервисе.

Пример: «Команда 1С (Бухгалтерия)» состоит из трёх групп. Люди между группами
почти не пересекаются, но пара разработчиков регулярно берёт работу соседей.

Деление нужно не всем командам, поэтому включается признаком на команде.

## Терминология

**Группа** — виртуальное подразделение внутри команды. Не «подкоманда», чтобы
слово «команда» в интерфейсе оставалось однозначным. Не «направление» — этим
словом описывается предметная область, а не люди.

## Ключевые решения

### 1. Реестр команд

Сегодня команда — свободная строка, приезжающая из Jira и продублированная в
шести местах (задачи, участие сотрудников, сценарии, ресурсные планы, элементы
бэклога, сотрудник). Сущности «команда» не существует, вешать признак не на что.

Заводится справочник команд. Наполняется автоматически из уже встречающихся
имён; ручной ввод не требуется. У записи — признак «делится на группы» и список
групп.

Побочный эффект: реестр закрывает давнюю дыру, когда опечатка в названии команды
в Jira порождала команду-двойник.

Строковое имя команды на существующих таблицах **не заменяется** ссылкой —
это сквозная миграция без пользы для задачи. Реестр адресуется по тому же имени.

### 2. Группа у сотрудника

Одна группа на сотрудника внутри команды. Истории (дат входа и выхода) нет.

История не нужна, потому что факт считается по группе задачи, а не по группе
человека, а состав команды в сценариях и так замораживается при утверждении.

Не проставлена — человек попадает в строку «Без группы».

### 3. Группа у работы

Разрешается лесенкой, по образцу категорий:

1. проставлена явно — решение человека, отображается чёрным;
2. унаследована от родителя — серым;
3. предположение по исполнителю (по его приписке) — серым.

Один эпик спокойно содержит задачи разных групп: инициативы и эпики создаются
одни на всю команду, деление проходит ниже, по задачам.

Подтверждение — в стопке разбора, второй колонкой рядом с категорией, уже
заполненной предположением. Подтвердить = согласиться.

Переезд задачи к другому родителю возвращает группу на переподтверждение —
так же, как сейчас поступает категория.

### 4. Куда попадают часы

- **Факт** — по группе задачи.
- **Ёмкость** — по группе человека.

Разработчик группы 1, отработавший в направлении группы 2: часы видны в факте
группы 2, а группа 1 видит, что её ресурс ушёл на сторону. Показывается
отдельной строкой «переток внутри команды».

Это **не** «помощь извне»: граница «свои — чужие» остаётся на уровне большой
команды. Существующий виджет помощи извне на группы не реагирует.

По команде в целом всё сходится: сумма по группам равна показателю команды.

### 5. Нормированные работы

Логика не меняется. Они привязаны к человеку, а у человека группа есть всегда.

### 6. Сценарий — один на команду

Внутри — разбивка потребности и ёмкости по ролям в разрезе групп плюс итог по
команде. Утверждается целиком.

Отвергнуто: три отдельных сценария на три группы. Тогда общая ёмкость команды
нигде не видна, а один человек может попасть в два сценария и дважды съесть свои
часы.

### 7. Ресурсное планирование — на команду целиком

План остаётся общекомандным, группы — только секции строк.

Из этого **бесплатно** следуют оба требования:

- график занятости сотрудника по дням строится по человеку сквозь все группы,
  поэтому перегруз невозможен;
- авто-распределение видит занятость в соседних группах: разработчик группы 1,
  занятый задачей группы 2, недоступен для группы 1 в эти дни.

Если бы план резался на три, потребовалась бы сверка между планами. Не режем.

### 8. Фильтр в шапке

Второй уровень (группа) появляется, только когда у выбранной команды включён
признак. У остальных команд шапка не меняется.

Ресурсное планирование и сценарии фильтру группы **не подчиняются** — они всегда
показывают команду целиком секциями, иначе ломается контроль занятости.

## Объём первого выпуска

- реестр команд, признак «делится на группы», состав групп;
- группа у сотрудника;
- разрешение группы у работы + колонка в стопке разбора;
- Ресурсы — ёмкость по группам;
- Сценарии — роли в разрезе групп;
- Ресурсное планирование — секции по группам;
- динамический второй уровень фильтра в шапке.

## Второй выпуск

Дашборд, Аналитика, KPI, Executive, Проекты, Стол тимлида, экспорты в xlsx,
Бэклог. До него витрины показывают команду целиком — не врут, просто не
детализируют.

## Безопасность и откат

Признак выключен у всех команд по умолчанию. Пока он выключен, поведение сервиса
идентично текущему: нет колонки в стопке, нет секций, нет второго уровня фильтра.
Выкатывать можно, ничего не включая.

Откат на любом этапе — снять признак. Полный откат — не вливать ветку.

## Критерии приёмки

1. Команда без групп ведёт себя идентично текущей версии. Главный тест: ловит
   основной риск правки.
2. Лесенка разрешения группы: явно > родитель > исполнитель.
3. Переезд задачи к другому родителю сбрасывает группу на переподтверждение.
4. Часы разработчика из чужой группы попадают в факт группы-заказчика и в расход
   ёмкости своей группы.
5. Ресурсное планирование не даёт перегрузить человека задачами из разных групп;
   авто-распределение учитывает занятость в соседних группах.
6. Сумма по группам равна показателю команды везде, где есть разбивка.
7. Сотрудник без группы виден в строке «Без группы», а не теряется.

## Техническое приложение

- Новые сущности: реестр команд (имя, признак деления), группа (принадлежит
  команде, имя, порядок), приписка сотрудника к группе.
- Группа задачи хранится по образцу категорий: явное значение отдельно,
  унаследованное и предположение вычисляются резолвером. Резолвер группы —
  сосед `CategoryResolver`, не встраивается в него.
- Ёмкость: `CapacityService` и `ResourceBaseService` получают необязательный
  разрез по группе; при выключенном признаке разрез пустой и запросы прежние.
- Сценарии: снапшоты состава команды дополняются группой сотрудника на момент
  утверждения — история приписок не нужна именно поэтому.
- `GET /teams` начинает отдавать структуру (имя, признак, группы) вместо плоского
  списка строк; плоский список остаётся для обратной совместимости фильтра.
- Миграции — Alembic, batch mode для SQLite; проверить на PostgreSQL.
