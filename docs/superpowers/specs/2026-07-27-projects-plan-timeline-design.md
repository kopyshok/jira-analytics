# Раздел «Проекты»: план/факт, задачи, таймлайн + сводный экран портфеля

**Дата:** 2026-07-27
**Статус:** согласовано с PM (вариант B + сводка в пустой правой панели)

## 1. Проблема

На `/projects` сегодня видно только **факт**: часы по категориям (бублик «Структура
трудозатрат»), участники, топ-3 задачи, AI-саммари. Нет плановых часов, нет списка задач
проекта с часами и статусом, нет сроков.

РП не может ответить на три вопроса:
1. Какие задачи у проекта и сколько на каждой списано.
2. Сколько план / сколько факт, по видам работ.
3. Где мы сейчас по срокам — по одному проекту и по всем сразу.

Всё это уже есть на рабочих столах аналитиков (`/desk/<токен>`), но в персональном срезе:
виджеты «Мои проекты» и «Таймлайн моих проектов» показывают долю **одного сотрудника**.

## 2. Решение — три точки входа

### 2.1 Карточка проекта → третья вкладка «План и сроки»

Переключатель в шапке карточки становится `Анализ | Презентация | План и сроки`.
Существующие две вкладки **не меняются** — PM подтвердил, что текущая аналитика устраивает
(она про детализацию и AI-саммари).

Содержимое новой вкладки, сверху вниз:
1. **Полоса план/факт** — как шапка виджета «Мои проекты» на столе, но по проекту целиком:
   `факт / план ч`, `%`, затем кольца по видам работ, затем утопающая плашка «Внешние».
2. **Таймлайн фаз проекта** — строка на фазу (Анализ / Разработка / Тестирование / ОПЭ),
   месячная шкала, вертикаль «сегодня», затенённое окно квартала. Затеняется квартал,
   выбранный чипами Q1–Q4 в шапке списка слева.
   ОПЭ на таймлайне — **отдельная фаза** (у неё свои даты), в кольцах его нет (см. 3.1).
3. **Задачи проекта** — таблица прямых детей: ключ (ссылка в Jira), название, статус, часы.

### 2.2 Правая панель без выбранного проекта → сводный экран портфеля

Сейчас там заглушка `Выберите проект из списка слева`. Заменяется на сводку по всем
проектам, попавшим в текущий фильтр списка:
1. **Сводная полоса** — `N проектов`, `факт / план ч`, `%`, кольца по видам работ,
   плашка «Внешние». Суммы по всем проектам списка.
2. **Таймлайн портфеля** — строка на проект, фазы цветом, «сегодня», затенение квартала.
3. **Полоса сигналов** — компактные чипы (не KPI-плитки):
   `N проектов > 100% плана`, `N проектов без списаний 14+ дней`,
   `<вид работ> отстаёт: X% при Y% общей`.

Таблицу проектов **не дублируем** — список слева уже её роль. Плитки «прогноз»,
«помощь извне», «молчат» остаются на `/dashboard` (виджет «Проекты квартала»), здесь их нет.

### 2.3 Возврат к сводке

- Кнопка **«Сводка»** в шапке списка слева, рядом со счётчиком проектов.
- Повторный клик по выбранной карточке снимает выбор.

Оба ведут на `/projects` без ключа.

## 3. Данные

Ни одного нового поля в БД. Всё считается из существующих сущностей.

### 3.1 Плановые часы по видам работ

Источник — `ResourcePlanAssignment` проекта, через `BacklogItem.issue_id`.
Норма фазы = `_assignment_norm` (`hours_allocated`, иначе `BacklogItem.estimate_<role>_hours`).

**Горизонт — весь срок проекта, не квартал.** Проект может идти два-три квартала, назначения
живут в разных `ResourcePlan`. Поэтому:
- находим все `(year, quarter)`, где есть назначения этого проекта;
- для каждого квартала берём **свежайший** план (та же логика, что `_find_recent_plan`) —
  чтобы форки и baseline-копии не удваивали часы;
- суммируем нормы фаз по выбранным планам.

ОПЭ схлопывается в Анализ/Разработку по `BacklogItem.opo_analyst_ratio` (default 0.5) —
ровно как на столах. Итог: **три вида работ** — Анализ, Разработка, Тестирование.
Отдельного кольца ОПЭ нет.

### 3.2 Фактические часы

Сумма `Worklog.hours` по **всему поддереву** проекта, без нижней границы по дате
(накопительный факт с начала инициативы — согласуется с фиксом от 2026-07-06).
Верхняя граница — конец выбранного квартала.

Разнесение по видам работ — по роли автора ворклога (`Employee.role`):
роль РП засчитывается в Анализ.

### 3.3 Внешние часы

Часы авторов, не входящих в команду проекта (или с ролью без плитки), идут в отдельную
плашку «Внешние». В план/факт и процент загрузки **не входят**.

Состав команды — `_team_member_ids`: сотрудники команд + все с ролью QA (общий ресурс).
Команда проекта берётся из `Issue.team` корневого эпика; если поле пустое — из команды
свежайшего `ResourcePlan`, в котором есть назначения этого проекта; если и того нет —
все авторы считаются внутренними (плашка «Внешние» пустая).

В сводке портфеля состав команды определяется **по каждому проекту отдельно** и только
потом суммируется — иначе аналитик чужой команды на одном проекте испортил бы цифры всем.

### 3.4 Задачи проекта

Прямые дети корневого эпика (`Issue.parent_id == root.id`).
Для каждого: ключ, название, статус, часы = сумма ворклогов **по поддереву этого ребёнка**
(не только по нему самому — иначе часы, списанные на внуков, теряются).
Сортировка: по убыванию часов, затем по ключу.

### 3.5 Таймлайн

Полосы — назначения из тех же планов, что и в 3.1. Для карточки проекта строка = фаза
(несколько назначений одной фазы схлопываются в одну строку по `packLanes`).
Для портфеля строка = проект, все фазы в одну дорожку.

Границы шкалы — от минимальной до максимальной даты назначений (+ факт-спан), округлённые
до месяца. Окно квартала (из фильтра списка) затеняется.

Вертикаль «сегодня» — если попадает в диапазон.

## 4. Квартальный фильтр — утверждённый сценарий

**Ничего не меняем.** `ProjectsService.list_projects(year, quarter)` уже фильтрует через
утверждённый сценарий (`PlanningScenario` со `status='approved'` за нужный квартал →
`ScenarioAllocation` с `included_flag=True` → `BacklogItem.issue_id`), и это правильный
источник: утверждение сценария и есть акт постановки задач на квартал.

> История: первая редакция спеки предлагала перевести фильтр на Jira-поле «Цели»
> (`Issue.goals`, формат `3кв26`). Реализовано и **отменено** (`d773814` → `dd20228`)
> после уточнения PM: цели квартала — это состав утверждённого сценария, а поле «Цели»
> в Jira ведётся не всеми и полнотой не обладает (19 из 101 проекта в базе).

Следствия, важные для остальных разделов:

- **Команда** в квартальном режиме определяется по `PlanningScenario.team`, а не по авторам
  списаний. Это существенно: проект нового квартала, на который ещё никто не списывал часы,
  остаётся видимым при включённом фильтре команды. Сводка портфеля (§2.2) наследует то же
  поведение, потому что считается по тому же списку.
- Проект попадает в квартал, даже если в Jira-иерархии у него есть родитель — ограничение
  `parent_id IS NULL` в квартальной ветке не накладывается, утверждённая аллокация сама
  делает задачу «проектом квартала».
- Год + чипы Q1–Q4 в шапке списка остаются как есть.

## 5. Пустые состояния

| Ситуация | Поведение |
|---|---|
| У проекта нет назначений в ресурсном плане | Кольца показывают только факт, план `—`, процент не считаем. Подпись `План не заведён`. Таймлайн — пустое состояние `Нет плановых дат`. |
| У проекта нет ворклогов | Кольца показывают план и `0 ч` факта, `0%`. |
| Нет дочерних задач | Таблица задач — `Нет задач` |
| Список проектов пуст (фильтр ничего не дал) | Сводный экран — обычная заглушка `Нет проектов за выбранный квартал` |
| Все проекты списка без плана | Сводная полоса без процентов, только факт |

## 6. Backend

Новый модуль `app/services/project_plan_service.py`. Общие хелперы из
`work_desk_widgets.py` (`_subtree_ids`, `_assignment_norm`, `_team_member_ids`,
`_ROLES`, `_PHASE_ESTIMATE_FIELD`) выносятся в `app/services/plan_common.py`
и импортируются обоими — чтобы не тащить desk-модуль в projects.

> Это единственный рефакторинг существующего кода. Он нужен: без него либо дубль логики
> на 150 строк, либо импорт «столов» из «проектов» (склейка несвязанных модулей).
> `work_desk_widgets.py` уже 1295 строк — вынос общей части его облегчает.

Эндпоинты в `app/api/endpoints/projects.py`:

```
GET /projects/{key}/plan
    → { work_types: [{code,label,plan_hours,fact_hours,pct}],
        external_hours, total_plan, total_fact, total_pct,
        timeline: { start, end, bars: [{phase,label,start_date,end_date,status}] },
        children: [{key,title,status,jira_url,hours}] }

GET /projects/portfolio?year&quarter&teams&category&status_category&search
    → { project_count, total_plan, total_fact, total_pct,
        work_types: [...], external_hours,
        timeline: { start, end, rows: [{key,title,bars:[...]}] },
        signals: [{kind,text,severity}] }
```

`/portfolio` принимает те же фильтры, что `GET /projects`, чтобы сводка считалась ровно по
видимому списку.

Сигналы (`signals`) считаются на бэкенде:
- `overload` — проекты с `pct > 100`;
- `silent` — проекты без ворклогов 14+ дней;
- `lagging` — вид работ, чей `pct` отстаёт от общего более чем на 15 п.п.

Пустой список сигналов допустим — фронт тогда полосу не рисует.

## 7. Frontend

Новые файлы в `frontend/src/components/projects/`:

| Файл | Назначение |
|---|---|
| `plan/WorkTypeRings.tsx` | Полоса «факт/план + кольца + Внешние». Используется и вкладкой, и сводкой |
| `plan/PhaseTimeline.tsx` | Таймлайн: месячная шкала, полосы, «сегодня», затенение квартала. Режимы `by-phase` и `by-project` |
| `plan/ProjectTasksTable.tsx` | Таблица задач проекта |
| `ProjectPlanView.tsx` | Вкладка «План и сроки» — собирает три блока |
| `PortfolioView.tsx` | Сводный экран портфеля |
| `plan/PortfolioSignals.tsx` | Полоса чипов-сигналов |

Хуки: `usePlanDetail(key)`, `usePortfolio(filters)` в `frontend/src/hooks/useProjects.ts`.

Стили — существующие токены темы Aurora (`DARK_THEME`, CSS-переменные `--wt-analysis`,
`--wt-dev`, `--wt-test`, `--wt-ope`). Классы колец и таймлайна со столов (`desk-ring-*`,
`desk-tl-*`) **не переиспользуем** — они живут в `desk-theme.css`, привязанном к публичной
странице стола вне общего shell. Пишем свои, на тех же токенах.

`ProjectsPage.tsx`: при `key === undefined` вместо `<Empty>` рендерится `<PortfolioView>`.
`ProjectsList.tsx`: кнопка «Сводка» + повторный клик по карточке снимает выбор.
`ProjectDetailPanel.tsx` / `ProjectHeader.tsx`: третье значение `ViewMode = 'plan'`.

Фильтры списка поднимаются из `ProjectsList` в `ProjectsPage` (сейчас они локальный стейт),
чтобы `PortfolioView` считал сводку по тому же набору.

## 8. Тесты

Backend (`tests/services/test_project_plan_service.py`):
- план по видам работ суммируется по нескольким кварталам без задвоения форков;
- ОПЭ раскидывается по `opo_analyst_ratio`;
- факт берётся по всему поддереву, накопительно;
- часы внешних авторов не попадают в план/факт;
- часы ребёнка включают его поддерево;
- проект без назначений → план `None`, процент не считается.

Backend (`tests/api/test_projects_endpoints.py`):
- `/projects/{key}/plan` 200 + 404 на неизвестном ключе;
- `/projects/portfolio` уважает те же фильтры, что список;
- квартальный фильтр по «Целям`: проект с `3кв26` попадает в `year=2026&quarter=3`,
  проект с пустым полем — нет.

Frontend: без новых E2E. Существующие спеки `/projects` должны продолжать проходить —
проверить, что заглушка «Выберите проект» больше не ожидается в тестах.

## 9. Что осознанно не делаем

- Не трогаем вкладки «Анализ» и «Презентация».
- Не добавляем таблицу проектов в сводку — список слева уже она.
- Не дублируем сигналы «прогноз» / «помощь извне» — они на `/dashboard`.
- Не делаем переключатель «квартал / весь срок» — горизонт всегда весь срок проекта,
  квартал только затеняется на шкале и фильтрует список.
- Не редактируем план из этого раздела — правка живёт в `/resource-planning`.
