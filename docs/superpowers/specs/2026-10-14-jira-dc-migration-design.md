# Переезд на Jira Data Center — дизайн

Дата: 2026-10-14. Ветка: `feature/jira-dc-migration`.

## Цель

Сервис перестаёт работать с Jira Cloud и переходит на Jira Data Center 11.3.7
(`https://jira.sun-team.ru`, только из внутренней сети). Существующая база
переводится на новые идентификаторы Jira одной процедурой «пробный прогон →
отчёт → применить», без потери служебных данных сервиса.

## Решения пользователя

| Вопрос | Решение |
|---|---|
| Облако | Поддержку Cloud убираем полностью |
| Способ перевода базы | Перепривязка существующих строк (внутренние UUID не меняются) |
| Сотрудники без совпадений по часам | Уникальное точное ФИО → автоматически; остальные — вручную в отчёте |
| Задачи, которых нет в новой Jira | Удалить, если у задачи нет служебных данных сервиса; иначе — решение в отчёте |
| Confluence | Тоже переехал на свой сервер — нужен свой адрес и токен |
| Репетиция на копии сервиса | Нет. Пробный прогон на рабочем; перед «Применить» — ручной дамп Postgres |

## Архитектура

Три части, один выпуск (клиент без перепривязки и блокировки выпускать нельзя).

### A. Клиент Jira DC

`app/connectors/jira_client.py`, `schemas.py`, парсеры в `sync_service.py`:

- Вход: `Authorization: Bearer <token>`; почта больше не нужна (`from_db`,
  `__init__`, настройки, `/settings/jira/test`, `ConnectionCard.tsx`).
- Базовый путь `/rest/api/2`.
- Поиск: `GET /search` с `startAt/maxResults/total`; `iter_issues` листает по
  `startAt`. Курсорный код (`nextPageToken`, `isLast`) удалить.
- Проекты: `GET /project` (массив).
- Пользователи: схема пользователя принимает DC-форму. **Идентичность
  сотрудника = `key`** (неизменяем при переименовании логина); логин `name`
  хранится в новом поле сотрудника и используется в JQL (`worklogAuthor`) и
  поиске `/user/search?username=`. Авторы ворклогов и комментариев — так же.
  Поле «Разработчик» (`userpicker`) → `key`.
- История статусов: `GET /issue/{key}?expand=changelog` (`changelog.histories`).
  `status_changed_at` в DC вычисляется из changelog: время последнего перехода,
  сменившего категорию статуса (категории — `GET /status`). Где задачи и так
  читаются поиском, использовать `expand=changelog` в поиске.
- Иерархия: `parent_key = fields.parent.key or Epic Link or Parent Link`.
  id полей Epic Link / Parent Link находятся по типу схемы и кэшируются в
  AppSetting, как `jira_sprint_field_id`.
- Опции полей: `GET /customFields/{n}/options`; облачный `/field/{id}/context`
  удалить. Резерв — JQL-скан, JQL по полю — `cf[N]`.
- Спринт: существующий разбор строкового формата оставить, добавить тест на
  настоящую DC-строку.
- Описание: wiki-строка сохраняется как есть.
- Ссылки на задачи: убрать жёсткий `example.atlassian.net` (`plan_common.py:28`
  и 7 компонентов фронта) — везде адрес из настроек (`useJiraBaseUrl`).
- Confluence: отдельные настройки «адрес» и «токен», вход Bearer, пути без
  `/wiki`, распознавание ссылок по хосту из настроек вместо `*.atlassian.net/wiki`.

### B. Блокировка синхронизации

- AppSetting `jira_migration_state`: `pending` | `done`. Миграция Alembic
  ставит `pending`, если в базе есть задачи, иначе `done` (свежая установка).
- Пока `pending`, отказывают с понятным сообщением: конвейер синхронизации,
  синк по расписанию, точечное обновление задач (стол тимлида, бэклог,
  `refresh_issues_by_keys`, `backfill_issue_author`). Проверка — в одном месте,
  через которое проходят все пишущие пути синка.
- Разрешены только чтения для переезда и настроек (проверка подключения,
  список полей, пользователи).
- Фронт: на странице синхронизации и в кнопках обновления — плашка
  «Синхронизация остановлена до завершения переезда» со ссылкой на страницу переезда.

### C. Страница «Переезд на новую Jira» (администрирование, только админ)

Новый сервис `app/services/jira_migration/` (разбит на модули по сущностям),
эндпоинты `app/api/endpoints/jira_migration.py`, страница в разделе
администрирования. Пробный прогон и применение — фоновые задачи с прогрессом
по существующему шаблону длительных операций.

#### C1. Пробный прогон (только чтение Jira, в базу пишет только отчёт)

1. **Поля.** Снимок текущих (облачных) значений всех `jira_*_field_id`,
   включая JSON плановых часов, сохраняется при первом прогоне и дальше не
   меняется. Для каждого — предложение поля DC по точному имени облачного поля
   (имена — константа в коде из `cloud_field_names.json`). Пользователь
   подтверждает или выбирает из списка полей DC, либо «не использовать».
2. **Проекты.** По ключу → новый `jira_project_id`.
3. **Задачи.** Постранично по проектам из scope: `key → id` DC (поля только
   `key`). Итоги: совпало по ключу; нет в DC и без служебных данных (будут
   удалены); нет в DC, но со служебными данными (решение: удалить / оставить);
   новые в DC (придут синком).
   Служебные данные задачи = любая строка в `backlog_items`,
   `issue_classifications` (только ручная), `plan_audit`, `project_ai_summaries`,
   `team_desk_marks`, `team_desk_daily_rates`, `scenario_allocation_snapshots`,
   `category_overrides` (по ключу), `scope_roots` (по ключу), либо ручные
   колонки задачи: `assigned_category`, `category_verified`,
   `assigned_subgroup_id`, `subgroup_verified`, `planned_*_manual`,
   `planned_hours_choice`. Точный список уточняется в плане.
4. **Сотрудники.** Все ворклоги DC: `/worklog/updated?since=0` → POST
   `/worklog/list` пачками по 1000. Отпечаток ворклога = (ключ задачи, начало в
   UTC до минуты, секунды). Смещение облачного «настенного» времени
   определяется автоматически: на выборке пробуются смещения −12…+14 ч,
   берётся дающее максимум совпадений.
   Для каждого сотрудника базы голосование по автору DC совпавших ворклогов:
   - **по часам** — лидер ≥ 90 % голосов и ≥ 3 совпадений;
   - **спорно** — иначе при наличии совпадений (кандидаты с числом голосов);
   - без совпадений → **по ФИО**, если ровно один пользователь DC с тем же
     ФИО (нормализация: регистр, ё→е, пробелы; без частичных совпадений);
   - иначе **не найден** — выбор пользователя DC поиском или «оставить без привязки».
   Если два сотрудника базы указывают на одного пользователя DC — спорно:
   привязку получает один, второй остаётся без привязки (слияние сотрудников —
   вне объёма).
5. **Часы.** Суммы по (команда задачи, месяц начала): база сейчас vs DC.
   Расхождения > 1 % подсвечиваются. Число ворклогов всего.
6. **Проверка возможностей.** Каждый используемый синком эндпоинт DC вызван
   хотя бы раз; ошибки — в отчёт.

Отчёт и решения пользователя хранятся в базе; решения переживают повторный прогон.

#### C2. Применить

Предусловия: свежий отчёт (< 24 ч), нет нерешённых пунктов, админ поставил
галочку «свежая копия базы сделана» (на странице — команда для сисадмина:
`docker compose exec postgres-backup /backup.sh`).

Одна транзакция:

1. Настройки полей: старые → новые id; JSON плановых часов; сброс
   автокэшей (`jira_sprint_field_id`, `jira_customer_field_id`,
   `jira_cost_type_field_id`).
2. Проекты: `jira_project_id`.
3. Задачи: сначала всем `jira_issue_id` префикс `cloud:` (снимает пересечения
   уникального индекса), затем новые id по ключу. Удаление по решениям.
   В `planned_hours_sources` / `planned_hours_choice` старые id полей → новые
   (отпечаток выбора пересчитывается так, чтобы выбор остался действительным).
4. Сотрудники: тот же приём с префиксом; новый `key` + логин. Непривязанные
   сохраняют старый id с префиксом `cloud:` и в синке не участвуют.
5. Облачные id людей → новые: `issues.assignee/reporter/developer_account_id`,
   `backlog_items.assignee_jira_account_at_choice`, `users.team_desk_filter_raw`
   (список разработчиков), `kpi_approvals.payload_json` (`account_id`).
6. Удалить все ворклоги и комментарии (на них ничего не ссылается; категории
   ворклогов пересчитываются).
7. `jira_migration_state = done`.

После фиксации — полная синхронизация задач и ворклогов из DC. После неё —
повторный расчёт часов по командам и месяцам и сравнение с отчётом «до».

Ошибка внутри транзакции — откат, база не меняется. Ошибка в синхронизации
после — данные чинятся повторным синком; полный откат — восстановление дампа
сисадмином.

## Проверка

- Фикстуры — обезличенные DC-ответы из `data/jira_check.txt` (имена и почты
  заменены), в репозиторий без персональных данных.
- Модульные тесты: схемы пользователя/автора, пагинация поиска, разбор
  спринта, иерархия из трёх полей, `status_changed_at` из changelog, опции полей.
- Сопоставление: отпечатки, определение смещения, голосование, ФИО, конфликт
  «двое на одного».
- Применение: пересекающиеся id (OS-91030 ↔ PMD-19591), удаление по решениям,
  перенос id людей во всех таблицах, атомарность — на SQLite и Postgres.
- Блокировка: каждый пишущий путь синка отказывает при `pending`.
- Второй скрипт админа — образцы того, что ещё не видели: `/project`,
  `?expand=changelog`, `/status`, `/customFields/{n}/options`, поиск с
  `expand=changelog`, `/user?key=`, Confluence `/rest/api/content`.

## Выкатка

1. Выпуск с A+B+C. После установки синк заблокирован.
2. В настройках — адрес и токен Jira, адрес и токен Confluence.
3. Пробный прогон, разбор отчёта, решения.
4. Сисадмин делает дамп. «Применить». Полная синхронизация. Сверка часов.

## Вне объёма

Поддержка Cloud; слияние дублей сотрудников; Tempo и прочие плагины;
перенос облачной истории, которой нет в DC.
