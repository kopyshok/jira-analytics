# «Первые шаги» — интерактивное начало работы — дизайн

Дата: 2026-09-28. Ветка: `feature/onboarding-first-steps` (экспериментальная — может быть снесена целиком).

Цель: новый пользователь проходит по порядку шаги настройки команды и знакомится с сервисом через
экскурсии по живым страницам (подсветка элементов с подсказками). Видео-инструкции — отдельный следующий
этап (см. «Вне объёма»), строятся из тех же сценариев экскурсий.

## Решения, принятые с PM

- Набор шагов выбирается **автоматически по состоянию команды**, без выбора роли. Одна панель, два блока:
  - **«Настройка команды»** — общий на команду. Отметки считаются по данным. Новичок в настроенной команде
    видит блок зелёным и свёрнутым («Команда настроена»).
  - **«Знакомство с сервисом»** — личный. Шаг отмечается, когда пользователь дошёл экскурсию до конца.
- Выполненный шаг **остаётся выполненным** (защёлка) — новые задачи не перекрашивают его обратно.
- Любой шаг можно **пропустить** и вернуть.
- Панель — кнопка в шапке рядом со «Справкой» с прогрессом «N из M». При первом входе открывается сама
  (один раз на пользователя). Все шаги закрыты или нажато «Больше не показывать» → кнопка исчезает;
  вернуть — кнопкой «Первые шаги» в шапке справки.
- Жёсткого мастера, блокирующего сервис, нет.

## Шаги «Настройка команды»

| # | id шага | Название | Когда выполнен |
|---|---|---|---|
| 1 | `issues_loaded` | Задачи команды загружены из Jira | авто: у команды есть задачи в охвате (сумма корзин `get_tree_counts` > 0) |
| 2 | `categorization` | Категоризация задач | авто: `stack / total ≤ 10%` при `total > 0` (те же счётчики) |
| 3 | `team_roles` | Состав команды и роли | авто: на сегодня в команде ≥1 активный участник и у каждого заполнена роль |
| 4 | `absences` | Отсутствия | вручную «Проверил» |
| 5 | `backlog` | Целевые задачи (бэклог) | авто: ≥1 неархивная инициатива команды с оценкой хоть по одной роли |
| 6а | `scenario_created` | Сценарий создан | авто: у команды есть ≥1 сценарий |
| 6б | `scenario_rules` | Нормированные работы проверены | вручную «Проверил» |
| 6в | `scenario_involvement` | Вовлечённость проверена | вручную «Проверил» |
| 7 | `resource_plan` | Ресурсное планирование | авто: у команды есть посчитанный план (`computed_at` не пусто) |

Шаг 6 в интерфейсе — один пункт с тремя подпунктами; выполнен, когда закрыты все три.

Напоминание шага 5 (текст в панели): бэклог наполняется автоматически из Jira — задачи, отнесённые на шаге 2 к
категории «Инициативы (на потом)», — и вручную кнопкой «Идея вручную» (для идей, которых ещё нет в Jira;
потом связываются с задачей). Дальше — приоритеты, оценки по ролям, параметры планирования (шестерёнка).

Шаг 1: если задач нет — подсказка «Синхронизация общая, по расписанию. Если задач команды нет — обратитесь к администратору».

## Шаги «Знакомство с сервисом» (личные)

Экскурсии: шапка (фильтр команды, период, справка), дашборд, аналитика, стол тимлида.
Шаг выполнен, когда пользователь дошёл экскурсию до последнего шага («Готово»); закрытие крестиком — не выполнен.

## Данные

### Отметки команды — таблица `team_onboarding_marks`
Строка на (команда, шаг). Поля: `id` (uuid), `team` (String 100), `step` (String 50), `state` (`done|skipped`),
`source` (`auto|manual`), `marked_by` (display_name, String 255, null для auto), `marked_at` (DateTime),
стандартные `created_at/updated_at`. Уникальность `(team, step)`.
Отдельные строки, а не JSON-поле: два тимлида одновременно отмечают разные шаги — без потерь записи.

Защёлка: при чтении статуса для авто-шага без строки считается живое условие; если выполнено — пишется строка
`state=done, source=auto`. Гонка двух одновременных чтений → нарушение уникальности ловится и игнорируется.
Авто-шаг со строкой больше не пересчитывается (заодно дорогой подсчёт категоризации идёт только до защёлки).

### Личное состояние — поле пользователя `onboarding` (Text JSON, по умолчанию `{}`)
`{ "completed_tours": [id...], "auto_opened": bool, "hidden": bool }`.
Паттерн — как `team_desk_filter` у пользователя.

Одна миграция: таблица + колонка. Миграция самодостаточная (не импортирует код приложения), идемпотентная по
новой таблице (в локальной базе её могли создать тесты раньше).

## API (`/api/v1/onboarding`, под общей авторизацией)

- `GET /status?team=X` → `{ team, steps: { <step>: { state: "done"|"skipped"|"pending", source, marked_by, marked_at } }, me: {completed_tours, auto_opened, hidden} }`.
  Без `team` — `steps: {}`.
- `PUT /team-steps/{step}` body `{team, state: "done"|"skipped"|"pending"}` — ручная отметка, пропуск, возврат
  (`pending` удаляет строку; для авто-шага защёлка при следующем чтении поставится снова, если условие выполнено).
  Неизвестный шаг → 404. Отметить `done` вручную можно только ручные шаги; авто-шаги — только `skipped/pending`.
- `PUT /me` body `{completed_tours?, auto_opened?, hidden?}` — частичное обновление личного состояния.

Тексты, порядок, группировка шагов и экскурсии — на фронте (статичная конфигурация). Сервер отдаёт только состояние.

## Фронтенд

- `frontend/src/onboarding/` — всё новое в одном месте:
  - `steps.ts` — конфигурация шагов (id, название, зачем, как, маршрут, экскурсия, ручной/авто, подпункты).
  - `tours.ts` — экскурсии: `{ id, route, search?, steps: [{ target: '<data-tour id>' | null, title, description }] }`.
  - `OnboardingContext.tsx` — провайдер в оболочке: запрос статуса, `openPanel()`, `startTour(id)`.
  - `OnboardingButton.tsx` — кнопка в шапке с прогрессом; скрыта, если всё закрыто или `hidden`.
  - `OnboardingDrawer.tsx` — панель: выбор команды (если в шапке выбрано несколько; ни одной → подсказка выбрать),
    два блока, у шага: статус, название, короткий текст, кнопки «Показать» (экскурсия), «Перейти», «Проверил»
    (ручные), «Пропустить»/«Вернуть»; для ручных — кто и когда отметил.
  - `TourRunner.tsx` — AntD `Tour`: по `startTour` переходит на маршрут (с нужной вкладкой), ждёт появления
    целей в DOM (до ~5 с), показывает шаги, чьи цели нашлись (цель не нашлась → шаг без привязки, по центру).
    Дошёл до конца → id экскурсии в `completed_tours`.
- Автооткрытие ждёт, пока не закрыто окно «Что нового» (нет непрочитанных заметок), чтобы два окна не всплывали разом.
- Цели экскурсий — атрибуты `data-tour="..."` на существующих элементах страниц (минимальные правки страниц).
- Вкладки: если страница управляет вкладкой через параметр адреса — экскурсия открывает её так; если локальным
  состоянием — добавить чтение начальной вкладки из параметра адреса (минимально).
- Автооткрытие: статус загружен и `auto_opened=false` → открыть панель и записать `auto_opened=true`.
- Реактивность: статус перечитывается при открытии панели и после своих отметок; серверные события не нужны.

Экскурсии настройки: категории, ресурсы → «Команда», ресурсы → «Отсутствия», целевые задачи, сценарии
(«Правила» + вовлечённость), ресурсное планирование. Шаг 1 — кнопка «Перейти» в синхронизацию, без экскурсии.

## Проверка

- pytest `tests/api/test_onboarding.py`: пустая команда → все `pending`; каждое авто-условие; защёлка переживает
  удаление данных; ручная отметка/пропуск/возврат; запрет ручного `done` для авто-шага; неизвестный шаг 404;
  `PUT /me` частичное обновление.
- Фронт: `npm run lint`, `npm run build`.
- E2E (Playwright, засеянная база): панель открывается, видны оба блока, «Показать» запускает экскурсию.
- Прогон на Postgres перед влитием в main (правило проекта).

## Вне объёма (следующие этапы)

- **Видео-ролики.** Робот автопроверок проигрывает сценарии из `tours.ts` на тестовой базе и пишет короткие
  ролики (10–30 с, без звука, с подписями); показываются по клику на весь экран; в экскурсию — через `cover`
  шага AntD Tour. Отдельная спецификация.
- Экскурсии для остальных разделов (проекты, KPI, сводка руководителя, тематический отчёт).
- Серверные события при отметке шага другим пользователем.
