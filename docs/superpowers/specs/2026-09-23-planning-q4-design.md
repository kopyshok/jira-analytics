## Часть 1. Быстрые правки

### 1.1 «Поднимать наверх» выключен — строка не двигается
Причина: оптимистичное обновление в `usePatchAllocation` (`frontend/src/hooks/usePlanning.ts:156-166`)
поднимает включённую строку наверх безусловно; сервер при `lift=false` порядок не меняет; refetch
возвращает строку назад, FLIP-анимация (`PlanningPage.tsx:333-381`) показывает оба прыжка.
Решение: условие подъёма `data.included === true && !wasIncluded && data.lift !== false`.
Тест: фронтовый unit (если есть инфраструктура хуков) или E2E-проверка порядка после клика при выключенном тумблере.

### 1.2 Авто-название сценария
`ScenarioCreateModal.tsx`: имя = `${year} Q${quarter} ${team}` (пример «2026 Q4 Команда 1С (ERP - Товарный учет)»).
Пересобирается при смене года/квартала/команды, пока пользователь не отредактировал поле имени вручную
(флаг «имя тронуто» в состоянии формы; сбрасывается при повторном открытии модалки). Без команды — `${year} Q${quarter}`.

### 1.3 Команда из глобального отбора
При открытии модалки: если `useGlobalTeamFilter().selectedTeams.length === 1` — подставить её в поле «Команда».

### 1.4 Переименование сценария
Бэкенд готов: `PATCH /planning/scenarios/{id}` принимает `name` (`planning.py:2222`). Фронт: название в шапке
(`PlanningPage.tsx:713-715`) → `Typography.Text editable` (или карандаш + инпут). Enter — сохранить через
`useUpdateScenario`, Esc — отмена, пустое имя не сохранять. Разрешено и для утверждённых сценариев.
Список сценариев в селекторе обновляется (хук уже инвалидирует список).

### 1.5 Ручные часы сразу видны в строке, сценариях и плане
Причина: `PlanEditService.edit/revert` (`app/services/plan_edit_service.py`) и разрешение конфликта пишут только
`Issue.planned_<role>_hours_manual`; строка списка, сценарии и ресурсный план читают копию
`BacklogItem.estimate_<role>_hours`, которая обновляется лишь в `BacklogService.sync_from_issue` при синке.
Решение (один источник правды — `Issue`):
- после `edit`, `revert`, `resolve_conflict` вызывать `BacklogService.sync_from_issue(issue)` (обновит копию и итог)
  и публиковать событие изменения бэклога (как другие правки — конвейер событий);
- инлайн-правка часов в строке (`PATCH /backlog/{id}`, `backlog.py:1028-1055`) по полям `estimate_*_hours` пишет
  через `PlanEditService.edit` (ручное значение в `Issue`), а не напрямую в копию — иначе синк её затирает;
- `BacklogPlanningParamsModal` передаёт в `PlanEditDrawer` значения «из Jira»/«действующее» из `Issue`
  (`planned_*_jira` / `planned_*`), а не из копии; после сохранения модалка перечитывает строку.
Тесты: pytest — правка через `/issues/{id}/plan` меняет `BacklogItem.estimate_*` и `estimate_hours`;
инлайн-правка переживает `sync_from_issue`.

### 1.6 Подвал «Загрузка по дням»: куда выбыл / откуда пришёл
В строку `employee_load` (`resource_planning.py:1004-1106`) добавить:
- `left_to`: `{date, team}` — если в квартале есть день вне команды после периода участия: дата выбытия и команда
  человека на следующий день (`tm.membership_rows` + `tm.team_on_day`); команда может отсутствовать → «не в командах»;
- `joined_from`: `{date, team}` — симметрично, если пришёл позже начала квартала (команда накануне даты вступления).
Фронт (`EmployeeLoadHeatmap.tsx`): под фамилией мелко «выбыл 11.08 → Команда 1С (Бухгалтерия)» /
«пришёл 01.10 из …»; подсказка по дню «вне команды» — «Не в команде · с 11.08 — Команда 1С (Бухгалтерия)».

## Часть 2. Дискавери и галочка «В план»

### Правило
`BacklogItem.included_in_planning` становится общей галочкой «В план» для **любой** целевой задачи
(колонка «В план» в списке и в развёрнутых дочерних строках RFA). `False` → задача не кандидат в сценарии.

Кандидатство в сценарий (вычисление кандидатов и черновых распределений):
1. `included_in_planning = False` → не кандидат (всегда).
2. **Служебные эпики** (задача совпала с правилом иерархии `require_parent=True`, т.е. сейчас Дискавери внутри RFA) —
   кандидат, если `included_in_planning = True`. Их часы идут **сверх** родителя: исключение «дети RFA в режиме
   целиком» (`mode_excluded_backlog_ids`, `backlog_service.py:245-257`) на них не распространяется.
3. Прочие явные листья (OS/PMD и т.п., правила без `require_parent`) — как сейчас, не кандидаты.
4. Режим `by_epics`: дети-эпики — кандидаты только при `included_in_planning = True`
   (сейчас галочка у детей хранится, но не учитывается — чинится этим же правилом).

Значение по умолчанию: `True` для всех, **`False` для служебных эпиков** — проставляется при создании
`BacklogItem` (в `sync_from_issue`, ветка `is_new`) и миграцией данных для уже существующих служебных эпиков
(у них сейчас нет распределений, т.к. они отфильтрованы как листья).

Существующая логика `set_planning_mode` (`backlog.py:1325`: при смене режима RFA перезаписывает её галочку)
остаётся.

### Реакция на переключение
- выключили → удалить распределения этой задачи из **черновых** сценариев (утверждённые не трогаем);
- включили → `_ensure_draft_allocations` (добавить в черновые сценарии её команды);
- событие изменения бэклога и сценариев (конвейер реактивности).

### Где правило применяется (все места, где сейчас стоит фильтр листьев)
`backlog_service.py:361-372` (создание черновых распределений), `planning.py:100-178, 622-623`
(кандидаты при создании/пересборке сценария), `mode_excluded_backlog_ids`. Дашборды, аналитика и «Целевые задачи»
как список инициатив — служебные эпики по-прежнему **не** считаются инициативами (показываются дочерней строкой).

### UI
- Колонка «В план» (переключатель) в `BacklogPage` и в `RfaExpandedRow` (заменяет существующий чекбокс детей).
- Выключенная строка — приглушена, остаётся в списке.
- Фильтр-метка «Не в плане · N».
- В модалке «Параметры планирования» существующий переключатель участия — тот же флаг.

### Тесты
pytest: служебный эпик создаётся с `False`, не попадает в черновик; включение добавляет в черновые сценарии сверх
родителя в режиме целиком; выключение обычной инициативы убирает из черновиков и не трогает утверждённые;
дети в `by_epics` с `False` не кандидаты.

## Часть 3. Несколько полей оценки и спорные оценки

### Настройка
Ключи `jira_planned_{analyst,dev,qa,opo}_hours_field_id` принимают JSON-список
`[{"field_id": "customfield_12431", "kind": "alt"|"sum"}, ...]`. Старое значение-строка читается как
`[{"field_id": <строка>, "kind": "alt"}]` (обратная совместимость; миграция не обязательна, но можно переписать).
Порядок в списке важен: первый «альтернативный» кандидат — значение по умолчанию при споре.
UI (`JiraFieldsCard.tsx`, блок «Плановые трудозатраты»): на роль — список строк «поле + переключатель
альтернатива/слагаемое», «+ добавить поле», удаление, перетаскивание порядка не обязательно (стрелки вверх/вниз).
Синк запрашивает все перечисленные поля (`_configured_planned_field_ids`).

### Расчёт значения роли (синк, `sync_service.py` `_new_plan_values`)
Кандидаты: каждое заполненное «альтернативное» поле — отдельный кандидат; все заполненные «слагаемые» —
один кандидат (их сумма), встаёт на позицию первого слагаемого в списке.
- 0 кандидатов → `None`;
- 1 кандидат или все кандидаты равны → это значение, спора нет;
- ≥ 2 разных → **спор**. Действующее Jira-значение = выбор пользователя, если он действителен, иначе первый кандидат.

### Хранение
`Issue`: новое поле JSON `planned_hours_sources` — `{role: {source_key: value}}` (source_key — `field_id`
или `"sum"`), обновляется синком. Новое поле JSON `planned_hours_choice` — `{role: {"source": source_key,
"fingerprint": <хэш кандидатов на момент выбора>}}`. Выбор действителен, пока хэш текущих кандидатов совпадает;
любое изменение в Jira → выбор недействителен → снова спор.
«Ввести своё» = существующее ручное значение (`planned_<role>_hours_manual` через `PlanEditService`), спор
считается решённым тем же fingerprint-механизмом (источник `"manual"`).
`planned_<role>_hours_jira` = действующее значение (как сейчас; остальной код не меняется).
После записи — `sync_from_issue` (часть 1.5) переносит в копию `BacklogItem`.

### API
- ответ списка бэклога: на строку `disputed_roles: [role]` и для каждой роли кандидаты
  `[{source_key, label, value}]` (label — имя поля Jira из кэша полей; для суммы «Back + Front»);
- `POST /issues/{id}/plan/choice` `{role, source}` (или `{role, manual_value}`) — сохранить выбор,
  пересчитать, `sync_from_issue`, событие.

### UI
- ячейка роли со спором: пунктирная оранжевая обводка + «?»; у строки метка «спорно»;
- фильтр «Только спорные · N» в `BacklogPage`;
- клик по спорной ячейке → поповер: радио-кандидаты с названием поля и значением, «Ввести своё», «Принять».

### Тесты
pytest: одно поле; две альтернативы равные — не спор; разные — спор, значение = первое; слагаемые суммируются;
сумма против альтернативы — спор; выбор действует до изменения значения в Jira; строковое старое значение
настройки читается.

## Часть 4. Привлечение сотрудников из чужих команд

### Термины
- **Опорный план команды на квартал**: основной план (`is_baseline`, иначе последний в статусе «Готово»)
  утверждённого сценария команды; если утверждённого нет — самого свежего черновика, с признаком
  «предварительно».
- **Привлечённый сотрудник** плана P: сотрудник, назначенный на фазу в P, но не состоящий в команде P на этот день.
- **Внешняя занятость** сотрудника E для плана P: часы E по дням из опорных планов **других** команд.

### Назначение исполнителей (`_assign_employees`, `resource_planning_service.py:1487`)
- Разработка: закреп вручную → сотрудник из поля Jira «Разработчик» задачи (`jira_developer_field_id`; если у самой
  задачи пусто — самый частый «Разработчик» среди её дочерних задач) — **из любой команды** → жадный выбор внутри
  команды, как сейчас.
- Анализ: закреп вручную → текущая логика (исполнитель, если в команде). Из чужой команды — только ручной выбор
  (исполнитель инициативы часто заказчик, авто-подстановка дала бы ложных привлечённых).
- QA — без изменений.
- Ручной выбор исполнителя фазы: поиск по всем активным сотрудникам, группы «Из Jira / Моя команда / Другие
  команды», у каждого — загрузка за квартал по всем опорным планам (%).

### Доступность и расчёт
- `build_availability` для E в плане P: календарь − отсутствия − **внешняя занятость** − (для своих сотрудников)
  дни вне команды. Для привлечённого дни «вне команды P» — норма, не блок и не конфликт `OUT_OF_TEAM`.
- Работает в обе стороны: авторасчёт домашней команды обходит часы, забронированные техкомандой в её опорном плане,
  и наоборот. Руками в домашнем плане можно поставить поверх.
- Конфликт пересечения: день, где часы E по всем опорным планам + текущему > ёмкости дня. Помечается в плане
  команды, для которой E — привлечённый (не домашней): фаза красная, текст «пересекается с планом <команда>».
  Считается при чтении диаграммы (живое), без автоматической пересборки чужих планов.
- Базовые ресурсы сценария (`ResourceBaseService`): из ёмкости сотрудника вычитаются часы, забронированные на него
  другими командами в их опорных планах квартала. 10% «Технических задач» не трогаем (РП уберёт сам).

### Диаграмма техкоманды
- Блок «Привлечённые» над задачами: на каждого привлечённого — строки только его фаз из опорных планов других команд
  («OS-91393 · Разработка · Пряничников», команда, «предварительно» если черновик). Только чтение, серая штриховка.
  Свободные окна видны как незанятые дни.
- Ответ `GET /resource-plans/{id}/gantt` получает `external_bookings: [{employee_id, team, issue_key, title,
  phase, start, end, daily_hours, provisional}]`.

### Домашняя команда
- В её диаграмме у E дни, занятые другими командами, — отдельный цвет (в строке сотрудника / подвале).
- Подвал: ячейка раскрашивается по доле «своя команда / другие команды»; легенда «домашняя команда / эта команда».

### Подвал техкоманды
Строки получают и привлечённых сотрудников (подпись «привлечён из <команда>»), загрузка двумя цветами.

### Вне объёма
Проверка ёмкости техкоманды на странице сценария по ролям, которых нет в самой команде (разработка), — пока
показывает нехватку; привлечённые появляются только на уровне ресурсного плана.

### Тесты
pytest: опорный план выбирается по правилу (утверждённый → черновик с флагом); внешняя занятость вычитается при
распределении в обе стороны; привлечённый не даёт `OUT_OF_TEAM`; ручное пересечение даёт конфликт в плане
техкоманды, не в домашнем; «Разработчик» из Jira подставляется из чужой команды; базовые ресурсы уменьшаются на
чужие брони.
