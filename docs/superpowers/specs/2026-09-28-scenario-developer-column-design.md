# Колонка «Разработчик» в сценариях — дизайн

Дата: 2026-09-28. Ветка: `feature/scenario-developer-column`.

## Зачем

Раньше разработчиков в сценариях не планировали: одна колонка «Исполнитель»,
разработку ресурсное планирование подбирало само (поле «Разработчик» из Jira
или жадный подбор). Теперь руководитель иногда заранее знает разработчика
задачи — его нужно указать в сценарии, и фаза «Разработка» в ресурсном
планировании должна автоматически уйти ему.

## Решения (согласованы с PM)

1. **Хранение** — на строке бэклога (`BacklogItem.developer_employee_id`, FK на
   `employees`, `ondelete=SET NULL`), как исполнитель. Одно значение во всех
   сценариях задачи и на странице «Бэклог».
2. **Только вручную.** Колонка пустая по умолчанию; синк из Jira её не пишет и
   не затирает. Поле «Разработчик» из Jira продолжает работать как раньше —
   молча, внутри ресурсного планирования, только для строк с пустой колонкой.
3. **Колонка «Исполнитель» → «Аналитик».** Содержимое и логика не меняются,
   ничего не переносим (около 630 строк, где исполнитель в Jira — разработчик,
   остаются как есть; руководители поправят в новых сценариях).
4. **Один человек — одна фаза.** Нельзя выбрать одного и того же человека
   аналитиком и разработчиком строки: в списке он неактивен с подсказкой. Сервер
   такой запрос отклоняет (422). Если совпадение возникло само (исполнитель в
   Jira сменился на выбранного разработчика), человек получает только
   разработку, анализ планировщик подбирает из пула аналитиков.
5. **Нехватка времени — всегда конфликт.** Разработчик из колонки ставится на
   фазу без проверки ёмкости; неразмещённые часы дают конфликт. Из другой
   команды — становится привлечённым.
6. **Охват:** сценарии, страница «Бэклог», выгрузка сценария в Excel
   («Бухгалтерия»), снимок сценария при утверждении (сравнение ревизий).

## Ресурсное планирование — фаза «Разработка»

Порядок выбора исполнителя фазы (часть 1):

1. Закреп вручную на диаграмме.
2. **Разработчик из колонки** (`developer_employee_id`) — без проверки ёмкости.
3. Колонка пустая → как сейчас: исполнитель строки с ролью разработчика
   (подтянутый из Jira — если хватает ёмкости, ручной — всегда) →
   «Разработчик» из Jira (если хватает ёмкости) → жадный подбор.

## Ресурсное планирование — фаза «Анализ»

- Колонка «Разработчик» заполнена → исполнитель строки (колонка «Аналитик»)
  идёт на анализ независимо от роли; если он совпадает с разработчиком — на
  анализ не идёт, анализ подбирается из пула аналитиков.
- Колонка пустая → как сейчас (фаза по роли исполнителя).
- Жадный подбор аналитика пропускает разработчика этой строки.

ОПЭ, распределение часов по ролям в сводке сценария и помесячная разбивка
снимка — без изменений (колонка «Разработчик» на них не влияет).

## Бэкенд

- Модель + миграция Alembic: `backlog_items.developer_employee_id`
  (String(36), FK employees SET NULL, index), relationship `developer`.
  Миграция идемпотентна (колонка может уже быть из `create_all` в тестах).
  Та же колонка `developer_employee_id` в `scenario_allocation_snapshots`.
- Сценарий: `AllocationResponse` получает `developer_employee_id`,
  `developer_display_name`. Новый `PATCH
  /planning/scenarios/{id}/allocations/{alloc_id}/developer` (только черновик,
  404 на неизвестного сотрудника, 422 если совпадает с исполнителем строки),
  публикует `entity_changed: planning`.
- `GET /planning/scenarios/{id}/assignee-candidates` — параметр `phase`
  (`analyst` по умолчанию | `dev`). Для `dev` группа «Из Jira» — «Разработчик»
  из Jira (`jira_developers_for_items`).
- Бэклог: `BacklogItemResponse` — `developer_employee_id`,
  `developer_display_name`. `BacklogItemUpdate` принимает
  `assignee_employee_id` и `developer_employee_id` (сейчас правка исполнителя на
  странице «Бэклог» молча отбрасывается — схема его не знает). То же правило
  422 при совпадении.
- Планировщик (`resource_planning_service`): разработчики из колонки — в набор
  привлечённых; правила выше в `_assign_employees`.
- Снимок: `developer_employee_id` пишется в `ScenarioAllocationSnapshot` и
  входит в `_ALLOC_COMPARE_FIELDS`.
- Excel: листы «Включено» и «Не вошло» — две колонки в конце, после «Цели»:
  «Аналитик» (имя как в колонке сценария) и «Разработчик». Итоговая строка
  суммирует только часовые колонки.

## Фронтенд

- `PlanningPage` + `BacklogAllocRow`: заголовок «Аналитик», новая колонка
  «Разработчик» справа от него (сетки `GRID` / `GRID_WITH_SUBGROUP`). Выбор —
  тот же компонент, что у аналитика, с кандидатами `phase=dev`; человек,
  стоящий аналитиком строки, неактивен («уже аналитик этой задачи»), и
  наоборот. В утверждённом — только чтение.
- `BacklogPage`: «Исполнитель» → «Аналитик», новая колонка «Разработчик» —
  выбор из активных сотрудников в любой строке; аналитик строки неактивен.

## Проверка

Тесты планировщика:
- разработчик из колонки получает фазу «Разработка»; без ёмкости — остаётся и
  даёт конфликт;
- пустая колонка — прежнее поведение (разработчик-исполнитель идёт на
  разработку, «Разработчик» из Jira работает);
- исполнитель = разработчик из колонки → только разработка, анализ другому;
- колонка заполнена, исполнитель-разработчик по роли → идёт на анализ.

Тесты API: PATCH разработчика (черновик/утверждён/совпадение/сброс), правка на
бэклоге, кандидаты `phase=dev`. Тест Excel: колонки на месте, итог считается.
