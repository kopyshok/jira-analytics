# Переезд на новую Jira — порядок действий

Для администратора сервиса и сисадмина. Выполняется один раз, после установки версии с поддержкой новой Jira. До завершения переезда синхронизация с Jira остановлена (на страницах синхронизации, бэклога и стола тимлида — плашка со ссылкой в раздел переезда).

## 0. Что понадобится

- Адрес новой Jira и личный токен учётной записи, которая видит все проекты сервиса и все списания. Почта не нужна.
- Адрес и токен Confluence, если сервис его использует.
- Сисадмин с доступом к серверу сервиса (папка с `docker-compose.yml`).
- Окно работ на применение: пока оно идёт, правки задач другими пользователями ждут. На данных промышленного размера это минуты. Полная синхронизация после него идёт часы, но уже без остановки работы.

## 1. Настройки

1. «Настройки → Подключение»: адрес и токен новой Jira → проверить подключение.
2. Там же — адрес и токен Confluence.
3. Настройки полей Jira до завершения переезда не меняются: сервис откажет с подсказкой. Первый пробный прогон запоминает прежние настройки полей, по ним предлагаются поля новой Jira, а выбираются они на вкладке «Поля» страницы переезда.

## 2. Пробный прогон

«Настройки → Администрирование → Переезд на новую Jira» (прямая ссылка `/admin/jira-migration`) → «Запустить пробный прогон».

Прогон читает все списания компании в новой Jira — это может занять десятки минут. Ход виден на странице, страницу можно закрыть. Данные сервиса не меняются, сохраняется только отчёт. Прогон можно повторять сколько нужно; решения, принятые по отчёту, сохраняются между прогонами.

## 3. Разбор отчёта

- **Проверка Jira** — все обязательные строки должны быть «Работает». «Не работает» в обязательной — к администратору Jira (права учётной записи, доступ к проектам).
- **Поля** — проверить предложения; где предложения нет — выбрать поле или «Не использовать». Если в споре оценок задач выбор приходился на поле, помеченное «Не использовать», после применения он сбросится (число таких задач видно на вкладке «Применить»).
- **Задачи** — по каждой исчезнувшей задаче с данными сервиса решить: «Оставить» или «Удалить». Исчезнувшие без данных сервиса удалятся сами. Список «Проекты, которых нет в новой Jira» — их задачи остаются как есть, решений не нужно.
- **Сотрудники** — фильтр «Нужно решение»: выбрать пользователя новой Jira (кандидаты или поиск) или «Оставить без привязки». Без привязки старая карточка останется без часов по перенесённым задачам: часы из новой Jira придут к новой карточке без команды — лучше найти и привязать учётку (сколько часов уйдёт — колонка «Часы уйдут к новой карточке»). Статус «Поиск не удался» значит, что Jira не ответила по этому человеку: он считается нерешённым — повторить прогон или привязать вручную. Статус «Конфликт» — нужного пользователя уже занял другой сотрудник: один пользователь новой Jira может принадлежать только одному сотруднику, для проигравшего нужно выбрать другого или оставить без привязки.
- **Часы** — посмотреть подсвеченные расхождения (больше 1 %). Сдвиг времени облачных списаний ожидается около +3 ч и «совпало» должно быть почти по всем проверенным списаниям. Если показано предупреждение, что сдвиг не +3 ч, сверка после переезда может расходиться сильнее.

## 4. Свежий прогон

Применить можно, только если пробному прогону меньше суток. Старше — запустить заново; решения сохранятся, новые спорные пункты, если появятся, будут отмечены на вкладках. Появившиеся после прогона новые сотрудники (их можно добавить из Jira, пока переезд не завершён) также требуют повторного прогона.

## 5. Копия базы (сисадмин)

Сразу перед применением, на сервере, в папке с `docker-compose.yml`:

    docker compose exec postgres-backup /backup.sh
    ls -lh ./backups/last/

Проверить целостность и свежесть файла (время — сейчас):

    gunzip -t ./backups/last/jira_analytics_prod-latest.sql.gz && echo OK

Сохранить файл и сообщить администратору. Подробности — `docs/backup-restore.md`.

## 6. Применить

Объявить окно работ. Вкладка «Применить»: препятствий нет → галочка «Свежая копия базы сделана» → «Применить» → подтвердить.

Применение — один шаг (одна транзакция): задачи, проекты, сотрудники и настройки полей переводятся на новую Jira; задачи удаляются по решениям; синхронизация разблокируется. Ошибка на любом этапе — база остаётся как была, текст ошибки показан на странице.

Пока применение идёт, правки задач другими пользователями ждут на блокировках базы. Если применение кажется зависшим — ждать; сервис посреди применения не перезапускать: при перезапуске транзакция откатится и ничего не изменится, тогда заново запустить пробный прогон и применить.

Что происходит со списаниями и комментариями:
- у задач, которые получают данные из новой Jira, списания удаляются и возвращаются полной синхронизацией: часы заново читаются из новой Jira;
- комментарии этих задач удаляются и не возвращаются: после переезда сервис комментарии не загружает;
- у задач, оставленных со старыми номерами (оставленные по решению и задачи проектов, которых нет в новой Jira), списания и комментарии сохраняются и больше не обновляются.

## 7. Полная синхронизация

Стартует сама сразу после применения: загружает задачи и все списания с самой ранней даты, что была в сервисе. Ход — «Синхронизация → история запусков» или статус на вкладке «Применить». Длится часы. Пока она идёт, держит блокировку синхронизации — вторая (в том числе по расписанию) не запустится; вручную её не запускать.

Если прервалась (перезапуск сервиса, ошибка) или не стартовала, потому что шла другая синхронизация, — кнопка «Запустить полную синхронизацию заново» на вкладке «Применить». Не использовать вместо неё режим «Полный» на странице синхронизации: он грузит списания только за 90 дней.

## 8. Сверка после переезда

Когда полная синхронизация закончилась — «Сверить после переезда» на вкладке «Применить». Результат — вкладка «Часы»: часы в базе сейчас против новой Jira на момент пробного прогона. Небольшая разница в текущем месяце — новые списания после прогона. Крупные расхождения в прошлых месяцах — разобрать (команда задачи, сотрудники без привязки).

## 9. Откат

Отменить применение можно только восстановлением копии из шага 5 и установкой прежней версии сервиса (та, что работала до переезда). Сисадмин, по `docs/backup-restore.md`, раздел «Восстановление из бэкапа»:

    docker compose stop backend
    docker compose exec postgres dropdb -U app jira_analytics_prod
    docker compose exec postgres createdb -U app jira_analytics_prod
    gunzip -c ./backups/last/jira_analytics_prod-latest.sql.gz | docker compose exec -T postgres psql -U app -d jira_analytics_prod
    docker compose start backend

Дамп содержит всю базу, включая хеши паролей пользователей (см. «Хранение и безопасность» в `docs/backup-restore.md`), поэтому учётные записи вернутся в состоянии на момент копии. После восстановления сервис снова в состоянии «переезд не завершён», синхронизация остановлена. Прежняя версия сервиса работает со старой (облачной) Jira; для новой попытки установить версию с поддержкой новой Jira и начать с шага 2.

## 10. Известные ограничения

- Проект, который появился в новой Jira позже применения, нужно подключать вручную: номера задач могут совпасть со старыми. Обратитесь к разработчику.
- Сотрудники, у которых в старой системе в ФИО была «е», а в новой Jira «ё» (или наоборот), могут не найтись автоматически — привязать вручную на вкладке «Сотрудники».
